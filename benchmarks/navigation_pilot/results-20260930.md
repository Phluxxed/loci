# Ember navigation pilot: vanilla, production Loci, source context

## Result

**Vanilla Codex was fastest and used the fewest tokens on this task. All three
answers were correct.** The new source-context branch improved on production
Loci, but still required more time, tokens, and navigation operations than
vanilla. Automatic graph delivery had no demonstrated benefit to the answer or
chosen route in this observation.

This is one task and one episode per condition, not a statistical result or a
general conclusion about large repositories.

## Answer quality

An independent reviewer scored anonymized answers before seeing condition
labels or metrics. All three correctly explained:

1. Approval materializes Work, reconciles dependencies, and saves ship blocked.
2. Status shows build as the blocker; human CLI output differs from chat actions.
3. Completing build reconciles ship to ready in the same save.
4. A stale stored-ready status still produces an informational chat run action.
5. Execution checks actual dependencies before transition and Codex startup.
6. The refusal changes no graph state and saves no run receipt.

All implementation citations were source-grounded; no critical contradictions
were found. Two answers leave the normal post-completion chat action implicit
in their ready-action rule. All explain the reconciliation mechanism without
separately recommending an explicit stale-state repair, which the user did not
request. Auxiliary test claims were not needed for the implementation scores.

## How navigation differed

| Condition | Observed route |
| --- | --- |
| Vanilla | File discovery → searches → direct reads of all five owners → targeted rereads and tests |
| Production | File inventory → broad Loci query → exact file queries → 13 source continuations → focused test queries |
| Source context | File inventory → broad Loci query → status/proposals/chat queries → shell search → graph/execution queries → 13 continuations |

Both initial broad Loci queries were noisy. Production reported 391 candidates
with 388 omitted and selected benchmark-related anchors; source context
reported 350 with 347 omitted and returned proposal-test and RUNSHEET material.
Neither initial packet supplied the full implementation needed for the answer.
The agents then narrowed the search themselves.

From turn submission, all five owners had returned some source content through
vanilla shell reads by **31.6 s**, production Loci by **47.4 s**, and new Loci by
**68.2 s**. Some production snippets were only one line. The new arm had already
seen actual graph/execution lines through shell search at **51.3 s**. Complete
Loci read coverage of those owners arrived at **114.8 s** in production and
**136.6 s** in the new arm. Vanilla's combined Code Mode output was clipped and
prompted rereads: early command completion does not prove complete
model-visible coverage.

Median observed retrieve duration was **1.27 s** in production versus **0.039 s**
in the new version. Median read duration was **1.00 s** versus **0.028 s**.
Summed observed Loci call durations were **26.96 s** versus **1.26 s**. These
include call waiting and may overlap; they are not total episode latency or a
causal estimate of graph cost. The much faster calls did not remove the
additional model work, queries, and paging.

show every shell/Loci operation, request, source extent, status, and completion

## What the graph contributed

Production returned **86 relationship records, 79 distinct by endpoints, type,
and evidence location**: 37 imports, 26 references, 10 calls, and 6 type uses.
It supplied real static links between relevant modules, such as chat importing
status/proposals/execution and status/proposals importing graph.

No returned relationship established the central approval-to-reconciliation,
claim-to-guard, or transition behavior. Both Loci agents read those owners'
source directly. Exact filenames were also available through shell discovery.
The trace proves relationship delivery and availability; it does not show that
the graph improved the chosen route or the answer. It also does not prove those
edges are absent from the full graph. Retrieve packets were partial and
reported candidate, source-preview, budget, or unresolved coverage omissions.

All production delivered records, with provenance, are in
[production-relationships.json](/Users/brummerv/phluxxed/tmp/loci-navigation-pilot-20260930-141931/assessment/production-relationships.json).
The source-context operation intentionally selected no relationships.

## Judgment and limits

This observation supports simplifying the normal path: the new version used
less time and fewer tokens than production while preserving answer quality.
The experiment does not isolate the contribution of each code change. It does
**not** show that Loci improved this task over ordinary Codex navigation. The
remaining overhead is visible in noisy initial selection,
many continuation calls, and continued shell use.

For the smallest-useful-context goal, graph delivery has no demonstrated win
here. Source selection and paging are useful follow-up questions; they are not
additional requirements for this completed pilot. Larger repositories,
different languages, and tasks with less obvious source owners remain untested.

Run order was fixed, model behavior can vary, instruction packages differ as
declared, and prompt-cache warmth was uncontrolled. Source found in native
receipts is not proof of attention or reliance. This pilot cannot establish
general latency, accuracy, impact-analysis coverage, or a statistical winner.

Earlier preflight failures and the interrupted, self-indexing run remain
preserved in the [runner history](README.md). They are not substituted into the
completed-run comparison or hidden as retries.
