Start with `src/continuity/service.ts:303-432`, especially `checkpointActiveTask`.

- MCP input requires a bound work context plus `checkpointId` and either `{state, summary, nextStep}` or `{state:"clear", outcome}` (`src/mcp/tools.ts:213-233`). The handler resolves the binding then calls the service (`src/mcp/tools.ts:805-828`).
- The service derives a deterministic event ID from `workspace.key + "\0" + checkpointId` (`src/continuity/service.ts:303-306`), writes a `next_action` event for an active/waiting task, then projects it into `current.json.active_task` with `next_step` (`src/continuity/service.ts:382-421`). It removes the same event from ordinary `next_actions`.
- Durable storage is `events.jsonl` plus `current.json`, under `continuity/workspaces/<workspace-key>/` (`src/continuity/workspace.ts:27-45`; writes at `src/continuity/store.ts:343-390` and `394-419`). SessionStart reads `current.json` and renders it into injected context (`bin/anvil.ts:656-681`; active task rendering is `src/continuity/render.ts:64-74`).

Retry semantics explain the stale-next-step symptom:

- **Same key, identical task content:** the existing deterministic event matches type, summary, and generated details (which include state, next step, and optional details), so no event is appended. If the projected frame is already correct, `changed:false`; if `current.json` drifted, the retry restores the active task using that same event (`src/continuity/service.ts:308-325`, `362-427`). The recovery is covered in `test/continuity-service.test.ts:409-423`.
- **Same key, changed task content (including a different next step):** it throws `VALIDATION_ERROR: checkpointId … was already used for different task content` before changing either stored event or active task (`src/continuity/service.ts:366-371`). Thus the old rendered next step remains until a checkpoint with a **new key** replaces it. A new non-clear checkpoint supersedes the prior task event (`src/continuity/service.ts:383-390`).
- **Clear:** a new clear checkpoint creates a `correction` event, resolves the prior active event, and writes `active_task: null`; it also removes that event from `next_actions` (`src/continuity/service.ts:382-421`). Retrying the same clear key is idempotent. Clearing with no initialized Continuity, or with no active task and no prior matching clear event, is rejected (`src/continuity/service.ts:372-377`). Tests cover replacement, clearing, and idempotent retry at `test/continuity-service.test.ts:425-458`.

Material uncertainty: this establishes the mechanism, but not the observed instance’s caller behavior. A retained old next step is consistent with a changed payload being submitted under a reused checkpoint key and its validation error being ignored, or with no subsequent checkpoint write at all.
