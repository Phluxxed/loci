Flow:

1. The MCP handler validates the host binding and calls it with `checkpointId` and task content: [tools.ts](/tmp/anvil-source-tasks-20260914/t09/src/mcp/tools.ts:805).
2. It derives a deterministic event ID from `workspace.key + checkpointId`: [service.ts](/tmp/anvil-source-tasks-20260914/t09/src/continuity/service.ts:303).
3. Under the workspace mutation lock, it appends the durable event to `events.jsonl`, then projects the task into `current.json`: [service.ts](/tmp/anvil-source-tasks-20260914/t09/src/continuity/service.ts:358), [store.ts](/tmp/anvil-source-tasks-20260914/t09/src/continuity/store.ts:379), [store.ts](/tmp/anvil-source-tasks-20260914/t09/src/continuity/store.ts:402). Those paths are per workspace: [workspace.ts](/tmp/anvil-source-tasks-20260914/t09/src/continuity/workspace.ts:30).
4. On the next SessionStart, the hook reads and renders `current.json`; its `active_task.next_step` therefore becomes injected Continuity: [anvil.ts](/tmp/anvil-source-tasks-20260914/t09/bin/anvil.ts:656).

A retry with the **same key and identical content** reuses the existing event. If the current projection already matches, `changed` is `false`; it appends no event. If `current.json` was lost or altered, the same retry restores the projection and returns `changed: true`, still without a duplicate event. This is directly exercised in [continuity-service.test.ts](/tmp/anvil-source-tasks-20260914/t09/test/continuity-service.test.ts:416).

A retry with the **same key and changed content** fails with `VALIDATION_ERROR` before writing. “Content” is the event type, summary/outcome, and computed details, which includes state, next step/outcome, and optional details; changing `nextStep` therefore cannot overwrite old text under the same checkpoint ID: [service.ts](/tmp/anvil-source-tasks-20260914/t09/src/continuity/service.ts:308), [service.ts](/tmp/anvil-source-tasks-20260914/t09/src/continuity/service.ts:317), [service.ts](/tmp/anvil-source-tasks-20260914/t09/src/continuity/service.ts:362). A new checkpoint ID is required when task text changes.

Clearing creates a durable `correction` event, links it to the prior task through `resolves`, and rewrites `current.json` with `active_task: null`; it does not erase history. A repeat of the same clear is idempotent. Clearing before initialization, or when no active task exists and no matching prior clear exists, fails: [service.ts](/tmp/anvil-source-tasks-20260914/t09/src/continuity/service.ts:373), [service.ts](/tmp/anvil-source-tasks-20260914/t09/src/continuity/service.ts:381), [service.ts](/tmp/anvil-source-tasks-20260914/t09/src/continuity/service.ts:403). The acceptance test confirms the cleared frame, resolution link, idempotent retry, and three retained events: [continuity-service.test.ts](/tmp/anvil-source-tasks-20260914/t09/test/continuity-service.test.ts:440).

So old next-step text on resume means the old active-task projection remained stored, or no successful new checkpoint superseded it. It is not silently updated by reusing the same key with changed text. Material uncertainty: this trace establishes the Continuity producer and Codex SessionStart consumer; it does not establish whether another host-level context source could independently add stale text.
