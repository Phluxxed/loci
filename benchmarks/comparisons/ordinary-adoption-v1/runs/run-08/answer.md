The binding selects the collaboration-space Continuity store; caller-supplied workspace-routing fields are rejected ([`src/mcp/tools.ts`](/tmp/anvil-source-tasks-20260914/t08/src/mcp/tools.ts:756)).
- A checkpoint key deterministically becomes `evt_task_<sha256(workspace-key, checkpointId)>` ([`service.ts`](/tmp/anvil-source-tasks-20260914/t08/src/continuity/service.ts:303)). Under the workspace lock, it appends that event once and projects the corresponding `active_task` into `current.json` ([`service.ts`](/tmp/anvil-source-tasks-20260914/t08/src/continuity/service.ts:357), [`store.ts`](/tmp/anvil-source-tasks-20260914/t08/src/continuity/store.ts:343), [`store.ts`](/tmp/anvil-source-tasks-20260914/t08/src/continuity/store.ts:394)). The store paths are `events.jsonl` and `current.json` per workspace ([`workspace.ts`](/tmp/anvil-source-tasks-20260914/t08/src/continuity/workspace.ts:30)).
- On the next SessionStart, the hook reads `current.json` and renders `active_task.summary`, state, and `next_step` into injected context ([`bin/anvil.ts`](/tmp/anvil-source-tasks-20260914/t08/bin/anvil.ts:656), [`render.ts`](/tmp/anvil-source-tasks-20260914/t08/src/continuity/render.ts:67)). This is why stale next-step text persists across a resumed task.

Retry behavior:

- Same key + identical task content: reuses the event, creates no duplicate, and returns `changed: false` if the projection already matches. It can still return `changed: true` to restore a lost/overwritten projection without appending another event ([`service.ts`](/tmp/anvil-source-tasks-20260914/t08/src/continuity/service.ts:362), [`service.ts`](/tmp/anvil-source-tasks-20260914/t08/src/continuity/service.ts:391), [`service.ts`](/tmp/anvil-source-tasks-20260914/t08/src/continuity/service.ts:413)). The acceptance test covers retry and recovery ([`continuity-service.test.ts`](/tmp/anvil-source-tasks-20260914/t08/test/continuity-service.test.ts:416)).
- Same key + changed task content, including a new `nextStep`: fails with `VALIDATION_ERROR` before any write, because type, summary, and derived details must exactly match the existing event ([`service.ts`](/tmp/anvil-source-tasks-20260914/t08/src/continuity/service.ts:317), [`service.ts`](/tmp/anvil-source-tasks-20260914/t08/src/continuity/service.ts:367)). The old projection therefore remains. A changed task needs a new checkpoint ID; that creates a replacement event that supersedes the prior active-task event ([`service.ts`](/tmp/anvil-source-tasks-20260914/t08/src/continuity/service.ts:386)).

Clearing requires a new key and `{ state: "clear", outcome }`. It records an active `correction` event, links it to and resolves the prior task event, sets `current.active_task` to `null`, and removes any same-event next-action projection ([`service.ts`](/tmp/anvil-source-tasks-20260914/t08/src/continuity/service.ts:373), [`service.ts`](/tmp/anvil-source-tasks-20260914/t08/src/continuity/service.ts:381), [`service.ts`](/tmp/anvil-source-tasks-20260914/t08/src/continuity/service.ts:403)). Retrying that exact clear is idempotent; the test confirms three total events for set, replacement, and clear ([`continuity-service.test.ts`](/tmp/anvil-source-tasks-20260914/t08/test/continuity-service.test.ts:440)).
